BO-SYS-001 · 1.0

Purpose and scope

A full-service hotel runs on a dozen disconnected systems — PMS, POS, work orders, messaging, radios, access control — plus, increasingly, robots from several vendors. Requests cross departments by phone and radio; robots run their own apps; nobody has one view of the work. build.os is the operating layer above those systems: it does not replace the PMS or POS, it connects them, turns every request into one kind of task, and dispatches that task to the right person, device or robot.

In scopeOut of scope
Cross-department task and workflow engine with SLAsReplacing the PMS, POS, payment processor or accounting system
Staff communication: messaging, push-to-talk, escalationGuest-facing booking engine
Multi-vendor robot dispatch, including doors and elevatorsRobot navigation stacks (owned by each robot vendor)
Integration bus to existing hotel systemsStoring card data (payments stay tokenised at the processor)
AI engine for intake, dispatch, forecasting and staff assistanceAutonomous AI actions that charge or move guests without approval
Operational analytics and KPI measurementBuilding management (HVAC/BMS) control; read-only telemetry later
BO-SYS-001 · 2.0

System context

build.os sits between people, devices and robots on one side and the property's existing systems on the other. The spatial model (spaces, routes, doors, elevators) is imported from Site Capture, so tasks and robots are located on surveyed geometry rather than hand-drawn maps.

BO-SYS-001 · 6.0

Robot fleet orchestration

Properties will run robots from more than one vendor. build.os treats every robot as an assignee for tasks and delegates navigation to the vendor stack, coordinating them through Open-RMF (the open-source ROS 2 framework for multi-fleet interoperability, with fleet, door and lift adapters and traffic management).

Task typeFlowDependenciesPhase
Delivery (F&B, amenity, retail)POS or guest request → load at outlet → elevator → door → hand-off → proof of deliveryPOS, lift adapter, guest notificationP1
Linen & waste transportScheduled runs between floors and back of house; housekeeping triggers ad-hoc runsService elevator, housekeeping systemP1
Room serviceAs delivery, with in-room hand-off rules and tray recovery taskPMS in-house statusP1
Security patrolScheduled routes from the Site Capture route graph; anomalies raise incidentsAccess control, video (read)P2
Inventory & supplyStore → outlet replenishment, par-level triggeredProcurement / inventory dataP2
Custom workflowsTemplate builder: any task type can name a robot capability as assigneeFleet capability registryP2
Doors and elevatorsEvery robot route that crosses a door or floor depends on an integration that varies by site: elevator vendor API or relay interface, and access-control API for doors. The door and elevator inventory from Site Capture (FU-SYS-001 S4) is the input to this per-site integration plan. Manual fallback (staff escort) is always defined.

Data, security and deployment

build.os holds guest identities, staff records and the operational history of a property. It follows the data classes defined for the Brain (CD-SYS-001 §1.3) and is deployed per property with an on-premises edge for anything that must keep working without the internet.

ControlImplementationStatus
DeploymentCloud control plane per tenant + on-prem edge gateway per property for robots, doors, elevators and push-to-talk (decision BO-D-01)design
Offline operationEdge keeps dispatch, robot control and PTT running through a WAN outage; syncs on reconnecttarget
Tenant isolationSeparate data stores and keys per property; no cross-property queries without explicit granttarget
Guest dataGuests referenced by PMS ID; message content is C2 and processed by local models onlytarget
PaymentsTokenised at the processor; no card numbers stored, minimising PCI DSS scopetarget
AccessRole-based by department; SSO; least privilege for integrationstarget
AuditEvery automated action and AI suggestion written to the append-only event logtarget
AssuranceSOC 2 Type II as the external attestation goal before multi-property rolloutP3
